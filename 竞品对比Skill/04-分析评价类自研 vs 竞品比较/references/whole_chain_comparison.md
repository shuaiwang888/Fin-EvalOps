# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `context` 可能包含历史提问、历史持仓/偏好、画像或用户自述；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `context` 的结构可能与自研不同，但仍需检查其中是否有用户画像或历史处境；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- 上下文主路径：
  - 自研使用 `self_record.context`；
  - 竞品使用 `competitor_record.context`；
  - 若编排层已提供归一化上下文字段，可读取归一化字段，但证据仍需回指原始字段。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出、上下文使用情况和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量答案：

1. **意图和上下文处理**
   - 是否识别了用户真实任务：归因、诊断、买卖决策、持仓调整、资产比较、风险控制；
   - 是否读取并使用了可见的持仓成本、风险偏好、投资期限、目标收益、亏损状态或历史追问；
   - 没有画像时，是否用分层假设、风险边界或必要追问处理，而不是伪装成私人化建议。

2. **工具选择**
   - 最新消息、政策、公司事件是否用 Search；
   - 结构化行情、财务、估值、基金、指数或持仓数据是否用 FinQuery；
   - 历史表现、回测、区间收益、相对强弱是否用 BackTest；
   - 需要全文或深层证据核验时是否补足 AccessingFullText 等工具；
   - 需要计算、排序或多指标汇总时是否合理使用 CodeInterpreter。

3. **查询设计**
   - 查询词是否贴合用户任务、标的、时间窗口和证据类型；
   - 是否补齐了最新催化、公告、财报、估值、持仓、规模、费率、客户、订单、供需、资金面等必要证据；
   - 是否避免用过宽泛、过时或错误类型的材料替代关键证据。

4. **证据覆盖与交叉验证**
   - 是否同时覆盖催化、基本面、估值、交易面、风险和用户适配；
   - 是否在工具结果之间做交叉核验；
   - 是否处理了冲突口径，而不是机械拼接。

5. **证据向答案的转化**
   - 查到的数据是否真正支撑了买卖判断、归因、持仓建议、风险提示或比较结论；
   - 是否存在“链路里查得不错，答案里却没有兑现”的断层；
   - 是否存在“工具很多，但仍然只输出资讯罗列或指标模板”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 -> 答案结果”的形式：
- 因为自研读取了持仓成本和风险偏好，所以最终能给出更合适的仓位与止损条件；
- 因为竞品补查了最新公告和财报口径，所以最终对催化持续性判断更稳；
- 因为自研只做了宽泛搜索、没有验证核心基本面或估值边界，所以最终建议偏空泛；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了行情、估值和公告证据，所以最终答案在事实边界上更稳。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把最终答案没有兑现的隐藏链路优点写成用户侧质量优势。
