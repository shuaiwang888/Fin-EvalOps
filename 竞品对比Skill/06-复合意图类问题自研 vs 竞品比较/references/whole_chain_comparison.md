# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中；

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list；

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量答案：

1. **意图拆解与任务编排**
   - 是否识别全部显性和隐性子任务；
   - 是否区分主任务和辅助任务；
   - 是否识别子任务之间的依赖关系；
   - 是否把用户真正需要的决策输出放在链路中心。

2. **工具选择**
   - 是否为任务选对了工具；
   - 新闻、政策、舆情或事件背景是否用 Search；
   - 结构化行情、财务、估值、资金、公司数据是否用 FinQuery / BackTest；
   - 需要预测、测算或复杂计算时是否使用 Forecast / CodeInterpreter；
   - 需要全文或证据核验时是否补足 AccessingFullText 等工具。

3. **查询设计**
   - 查询词是否贴合用户任务；
   - 是否补齐了最新新闻、公告、财务、行业、政策、案例、交易条件等必要证据；
   - 是否处理用户给定的时间窗口、对象范围、数据口径、对比对象；
   - 是否避免用过宽泛或错误类型的材料替代关键证据。

4. **证据覆盖与交叉验证**
   - 是否同时覆盖事实背景、数据口径、产业/公司层、交易/策略层信息；
   - 是否在工具结果之间做交叉核验；
   - 是否处理冲突口径，而不是机械拼接；
   - 是否避免编造案例、错用历史样本或误读工具输出。

5. **证据向答案的转化**
   - 查到的数据是否真正支撑了最终判断；
   - 多源信息是否被综合成结论，而不是表格或段落堆砌；
   - 是否形成事实、影响、传导、策略闭环；
   - 是否给出用户要求的可执行输出；
   - 是否存在“链路里查得不错，答案里却没有兑现”的断层；
   - 是否存在“工具很多，但仍然只输出资料拼盘”的伪复杂。

   - 是否存在重复检索、无效工具、过度规划；

## 如何解释答案差异

优先写成“链路动作 -> 答案结果”的形式：
- 因为自研先拆出了事实梳理、影响评估和策略建议三个子任务，所以最终答案覆盖更完整；
- 因为竞品只搜索背景新闻，没有补足财务或公告证据，所以最终影响判断停留在泛泛描述；
- 因为自研虽然调用了多个工具，但没有把工具结果综合成结论，所以最终仍然触发“信息堆砌无综合”；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了公告、行情和计算证据，所以最终在数据口径上更稳；

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把“回答更长”当作复合意图完成更好；
- 不用链路亮点抵消最终答案中的关键漏答、事实错误、数据口径错误或不可执行问题。
