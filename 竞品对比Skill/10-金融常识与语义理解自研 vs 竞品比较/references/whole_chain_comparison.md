# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量金融常识与语义理解答案：

1. **工具选择**
   - 是否为任务选对了工具；
   - 实体、产品、指标、财报、行情、持仓和盘中价格是否用 FinQuery 等结构化工具核验；
   - 新题材、黑话、公开规则、交易制度、最新背景是否用 Search 或 AccessingFullText 补足；
   - 需要计算、筛选、比较、清洗指标时是否使用 CodeInterpreter 或等价计算校验；
   - 定义类、规则类、产品边界类问题是否避免用 Forecast、BackTest 或纯行情数据替代概念解释。

2. **查询设计**
   - 查询词是否贴合用户真实对象、错别字纠正、别名、股票代码、产品类型和指标口径；
   - 是否区分公司与旗下基金、股票与 ETF/指数/现货、相似简称与相似代码；
   - 是否补齐 PE、ROE、ST、集合竞价、主力控盘、最新季度、盘中价格等规则或口径；
   - 是否避免机械接受负 PE、未披露报告期、过时价格或未消歧实体。

3. **证据覆盖与交叉验证**
   - 是否同时覆盖用户问题、概念定义、金融规则、实体/产品边界、数据口径和时点；
   - 是否在结构化数据、公开规则、公告/资料全文、行情时点之间做必要核验；
   - 是否处理冲突口径、异常数据和用户前提错误，而不是机械拼接；
   - 是否为错别字、黑话和新题材提供足够语义证据，而不是无证据强行联想。

4. **证据向答案的转化**
   - 查到的信息是否真正支撑了定义、边界、规则、口径和结论；
   - 是否存在“链路里查到了正确对象或规则，答案里却混用/漏写”的断层；
   - 是否存在“工具很多，但最终仍然只输出数据表、行情结果或泛泛建议”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 → 答案结果”的形式：
- 因为自研先做实体消歧并核验股票代码，所以最终没有把豪威集团和豪能股份混用；
- 因为竞品检索了集合竞价规则并把 9:20 与 9:25 的含义写入答案，所以交易规则更稳；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了最新行情和产品边界核验，所以最终答案在时点和对象上更可靠；
- 因为自研只把 FinQuery 表格搬进答案，没有解释微盘股定义或 PE 负值含义，所以链路没有转化为语义理解质量。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把链路中未进入最终答案的信息写成最终答案优势。
