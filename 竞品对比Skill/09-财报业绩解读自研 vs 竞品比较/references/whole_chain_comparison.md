# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量财报解读答案：

1. **工具选择**
   - 是否为任务选对了工具；
   - 结构化财务数据、行情、估值和历史指标是否用 FinQuery；
   - 公告、年报附注、季报变动原因、分红公告、问询函、业绩说明会或官网披露是否用 Search / AccessingFullText 补足；
   - 需要计算同比环比、占比、敏感性或差额闭合时是否使用 CodeInterpreter 或等价计算校验；
   - 需要复盘公告后股价表现或事件影响时是否使用行情/回测相关工具。

2. **查询设计**
   - 查询词是否贴合公司、报告期、指标、科目、公告名称和特殊事件；
   - 是否补齐财务数据、公告原文、业务/行业背景、价格、订单、成本、产品结构等必要证据；
   - 是否避免用宽泛新闻、通用公式或二手摘要替代关键原始披露；
   - 是否区分归母/扣非、单季/累计、调整前/调整后、会计口径变更和非经常性损益。

3. **证据覆盖与交叉验证**
   - 是否同时覆盖用户问题、财务指标、公司披露、业务或会计原因、投资含义；
   - 是否在结构化财务数据和公告全文之间做交叉核验；
   - 是否处理冲突口径、异常数据和用户前提错误，而不是机械拼接；
   - 是否把特殊事件拆到足够细的金额、科目和传导机制。

4. **证据向答案的转化**
   - 查到的数据是否真正支撑了归因、业务解释、持续性和投资判断；
   - 是否存在“链路里查到了公告主因，答案里却没有兑现”的断层；
   - 是否存在“工具很多，但仍然只输出公式、指标罗列或主观股价判断”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 → 答案结果”的形式：
- 因为自研读取了季报原文并命中公司披露主因，所以最终能解释现金流变化的真实来源；
- 因为竞品只查了结构化财务表、没有补足公告全文，所以最终停留在营运资本公式推导；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了公告全文和财务数据校验，所以最终答案在事实边界上更稳；
- 因为自研做了差额闭合和口径纠偏，所以最终能解释归母与扣非、调整前后或单季累计之间的差异。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把链路中未进入最终答案的信息写成最终答案优势。
