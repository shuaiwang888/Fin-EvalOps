# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量答案：

1. **工具选择**
   - 是否为任务选对了工具；
   - 事件背景是否用 Search；
   - 结构化金融数据是否用 FinQuery / BackTest；
   - 需要全文或证据核验时是否补足了 AccessingFullText 等工具。

2. **查询设计**
   - 查询词是否贴合用户任务；
   - 是否补齐了最新新闻、公告、主营、供货、产能、客户、订单等必要证据；
   - 是否避免用过宽泛或错误类型的材料替代关键证据。

3. **证据覆盖与交叉验证**
   - 是否同时覆盖事件、产业链、公司层和交易层信息；
   - 是否在工具结果之间做交叉核验；
   - 是否处理了冲突口径，而不是机械拼接。

4. **证据向答案的转化**
   - 查到的数据是否真正支撑了最终排序、受益逻辑和结论；
   - 是否存在“链路里查得不错，答案里却没有兑现”的断层；
   - 是否存在“工具很多，但仍然只输出概念罗列”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 → 答案结果”的形式：
- 因为自研补查了主营/客户/产能证据，所以最终能把核心受益与边缘受益分开；
- 因为竞品只做了宽泛搜索、没有补足结构化验证，所以最终排序依据偏虚；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了公告与测算，所以最终答案在事实边界上更稳。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案。
