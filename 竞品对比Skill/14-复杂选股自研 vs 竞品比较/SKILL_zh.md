# 复杂选股自研 vs 竞品比较评测协议

本协议用于比较**同一 `case_id`（同题配对键）下**自研模型与一个竞品模型在复杂选股任务上的**整体链路 + 最终回答**。它沿用第 14 类复杂选股的绝对评分体系（rubric、golden cases、root cause、cap rules），并额外定义 pairwise 比较协议与链路差异解释方法。

## 协议边界

- **绝对评分**：判断单个模型在复杂选股任务上答得好不好。
- **横向比较**：
  1. 对同题两边分别做绝对评分；
  2. 再比较自研强项、自研弱项和竞品强项；
  3. 最后用两边完整链路解释这些答案差异是怎么产生的。
- 比较对象不是“两个最终答案”这么窄，而是：
  - 同一用户问题；
  - 两边最终回答；
  - 两边可见整体链路，包括 `chain[*].plan`、`chain[*].tools[*]`、工具输入、工具输出，以及可用的可视化答案 `answer`。
- 链路的价值在于解释答案差异，不是脱离答案单独评判“工程美学”。复杂选股类任务最终以**条件是否保留、金融口径是否正确、筛选规划是否可执行、候选池和排序是否可核验**为核心。

## 适用范围

仅在以下条件同时满足时使用本协议：
- 题目属于复杂选股任务，包括长条件量化选股、复杂交易形态筛选、带定性约束的推理选股、结构化条件与非标信息混合筛选、跨领域或分层筛选；
- 输入中存在同一 `case_id` 对应的两份记录；
- 两份记录分别代表自研模型与**一个**竞品模型；
- 当前任务目标是回答：
  - 自研模型相比竞品好在哪里；
  - 自研模型相比竞品差在哪里；
  - 竞品模型哪里值得学习。

不适用于：
- 普通单模型质检；
- 不同问题之间的横向比较；
- 一次同时比较多个竞品模型；
- 普通单只股票诊断、简单行情查询、纯事件概念受益排序、投资组合/KYC 推荐或一般知识问答；
- 只看最终答案、完全不需要链路归因的轻量 benchmark。

若问题核心是“事件/概念受益标的排序”，优先使用 `01-event-and-concept-stock-selection` 的比较协议；若核心是长条件、多阶段、技术形态或结构化+非标混合筛选，用本协议。

## 输入语义

每次评测至少读取：
- `case_id`：同题配对键（自研与竞品共享）；
- 用户问题；
- 自研模型完整记录；
- 竞品模型完整记录。

### 最终答案锚点

- 自研模型：优先使用 `text_answer` 作为最终答案主锚点；
- 竞品模型：若 `text_answer` 为空，则使用 `answer` 作为最终答案主锚点；
- 若编排层已提前生成统一字段，可直接读取归一化后的最终答案，但不得因此改变原始证据指针；
- 可视化答案 `answer` 仅在评估表格、图表、字段和呈现质量时参考，不得替代 `text_answer` 的主要结论锚点。

### 真实链路结构

- `tool_usage` 是**评测维度名**，不是输入 JSON 的字段名；
- 真实工具调用从 `chain[N].tools[M]` 读取；
- 顶层 `tools` 字段即便存在，也可能为空，不能把它当成主要链路来源；
- 自研记录通常是多步 `chain`，`plan` 较完整；
- 竞品记录可能只有一个 `chain` step，`plan` 为空，但 `chain[0].tools` 仍包含可用的工具调用证据。

详细规则见：
- [references/comparison_protocol.md](references/comparison_protocol.md)
- [references/whole_chain_comparison.md](references/whole_chain_comparison.md)

## 执行协议

0. **先分析题目，建立共享评测框架**
   阅读 [references/rubric/_index.md](references/rubric/_index.md)，仅依据用户问题和必要上下文抽取：
   - 显性筛选条件、否定条件、范围条件、排序/字段要求；
   - 隐性金融语义、业务口径、先后关系和分层筛选关系；
   - 哪些条件应结构化取数，哪些条件应搜索/公告/研报验证，哪些条件当前数据不可用或需用户确认。

   对维度判断适用性并分配动态权重。同一题下，自研与竞品必须使用**同一套**适用性和权重，避免把权重差异误当成模型差异。动态权重总和必须为 100。

   同时阅读 [references/golden_cases/_index.md](references/golden_cases/_index.md)。命中专家案例或同类语义时，必须使用对应 hard checks。若涉及图片批注中沉淀的业务知识，继续阅读 [references/golden_cases/image_annotation_anchors.md](references/golden_cases/image_annotation_anchors.md)。

1. **先分别做绝对评分**
   对自研与竞品分别按本 skill 定义的 8 个维度评分：
   - `intent_condition_extraction`
   - `financial_semantics_and_caliber`
   - `screening_plan_decomposition`
   - `tool_usage`
   - `result_correctness_and_coverage`
   - `ranking_and_decision_actionability`
   - `data_logic_time_boundary`
   - `composition_credibility`

   仅对 `relevant` 和 `supplementary` 维度评分，跳过 `not_applicable` 维度。除 `tool_usage` 外，先只依据用户问题和各自最终答案评分；不得因为另一方更差，就抬高本方绝对分。

2. **再分别诊断两边整体链路**
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md)、[references/tool_list/_index.md](references/tool_list/_index.md) 和 [references/whole_chain_comparison.md](references/whole_chain_comparison.md)。
   对两边分别检查：
   - 是否正确拆解长问句、保留条件、区分硬条件/软条件、处理先后依赖和排序；
   - 工具选择是否正确，例如结构化行情/财务数据、回测统计、全文公告、搜索、代码计算是否各司其职；
   - 查询输入是否贴合指标字段、日期窗口、交易周期、题材/合作关系/订单/核心技术等非标约束；
   - 证据是否覆盖了题目真正需要的条件明细、候选池、字段、排序和边界；
   - 工具结果是否真正转化成了更准确、可复核、可执行的最终答案。

   当 `plan` 存在时，可结合其判断意图、拆解和筛选推理；当 `plan` 为空时，不强行编造“推理文本”归因，优先依据工具行为、证据流、候选结果和最终答案做判断。此时评分 `tool_usage`。

3. **应用封顶规则**
   按需读取 [references/rubric/](references/rubric/_index.md) 中的 `cap_*.md` 文件。
   对自研与竞品分别检查封顶规则。封顶规则限制最终分，不替代维度评分。若多个封顶同时触发，取最低上限。

4. **最后做 pairwise 比较**
   阅读 [references/comparison_protocol.md](references/comparison_protocol.md)。
   在双方绝对评分完成后，逐维比较：
   - 自研真正做得好的地方；
   - 自研真正落后的地方；
   - 竞品真正值得学习的地方；
   - 双方共同失败点；
   - 哪些链路差异导致了最终答案差异。

   比较时必须坚持：
   - **先绝对、后相对**：双方都差时，先写共同短板，再写谁相对更好；
   - **答案与链路合看**：答案决定质量，链路解释质量是怎么形成的；
   - **复杂选股正确性优先**：条件、口径、分层时序、候选池、排序和字段任一核心环节错误，都不能被流畅表达或复杂链路掩盖；
   - **证据优先**：每条优势、弱点和学习点都要绑定最终答案或链路证据；
   - **不做多模型聚合**：本协议一次只比较一个竞品，跨竞品总结由后续汇总层完成。

5. **序列化输出**
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。
   先输出结构化 JSON，再附简短自然语言评审。

## 保守评分

- 自研与竞品使用同一维度、同一权重、同一 hard checks；
- 不因为相对胜负而改变绝对评分；
- 不因为链路看起来繁复就自动加分；
- 若链路更好但最终答案没有兑现，优点只能记为链路信号，不能替代答案质量；
- 若长问句核心条件、金融口径、时间窗口、候选池、排序或字段输出有硬伤，即便表达更完整也必须扣分并按需触发封顶规则；
- 若双方都没有真正完成用户任务，必须明确输出共同不足，不能把“谁稍微好一点”写成高质量答案。

## 安全护栏

本 skill 的评分安全护栏，尤其包括：
- 对长问句，遗漏一个核心条件、把或关系拆成且关系、把重复强调当成两个条件，都会实质改变候选池，应严肃扣分；
- 对金融口径，均线、MACD、KDJ、资金流、龙虎榜、北向、退市风险、主线题材等必须按业务含义处理；
- 对分层筛选，必须保留先后关系、跨领域交集、二次验证、排序和输出字段；
- 对非标条件，不能把用户原问句整句丢给搜索；应拆出聚焦关键词，如主线题材、合作关系、订单、极端利好、核心技术等；
- 对不可用、停更或低频数据，必须说明边界或询问用户，不能强行给确定结果；
- 惩罚数据堆砌。大量表格、图表或过程说明没有帮助用户判断谁符合条件、为什么排序、下一步怎么用，不是好答案；
- 要求结果可核验。候选股、数值、公式、字段和事实必须能从最终答案或链路证据追溯。
