# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量答案：

1. **工具选择**
   - 是否为任务选对了工具；
   - 最新政策、新闻、公告、市场传闻或热点背景是否用 Search；
   - 结构化行情、财务、公司和行业数据是否用 FinQuery / BackTest / Forecast；
   - 需要阅读全文、公告原文、研报或政策原文核验时是否补足 AccessingFullText；
   - 涉及截图、图片批注、公告图片或社媒图片时是否使用 SearchImage 或对应工具。

2. **查询设计**
   - 查询词是否贴合用户任务；
   - 是否补齐时间锚点、发布时间、来源层级、事件进展、公司主体、政策文件名、公告口径等必要条件；
   - 是否区分“官方确认”“媒体报道”“市场传闻”“研报推断”“交易异动解读”等证据类型；
   - 是否避免用过宽泛、过旧或错误类型的材料替代关键证据。

3. **证据覆盖与交叉验证**
   - 是否同时覆盖政策/事件层、公司/产业层、市场交易层和投资映射层；
   - 是否在工具结果之间做交叉核验；
   - 是否处理冲突口径、时间不一致、旧闻复炒、传闻未证实等问题；
   - 是否把来源、时间和事实口径保留到最终答案中。

4. **证据向答案的转化**
   - 查到的信息是否真正支撑了最终意图满足、事实边界、证据质量、资讯整合、投资映射、核心信号提炼和非标准资讯边界；
   - 是否存在“链路里查得不错，答案里却没有兑现”的断层；
   - 是否存在“工具很多，但仍然只输出模板化建议或宽泛概念”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 → 答案结果”的形式：
- 因为自研补查了政策发布时间和原文口径，所以最终没有混淆旧政策与新变化；
- 因为竞品覆盖了公告、研报和交易异动三类证据，所以对市场催化的解释更稳；
- 因为自研只做宽泛搜索，没有验证公司主体和受益环节，所以最终投资映射偏虚；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了最新新闻和结构化数据，所以最终答案在时效和事实边界上更可靠。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把未核验传闻、市场小段子、调研纪要中的非公开细节当成确定事实。
