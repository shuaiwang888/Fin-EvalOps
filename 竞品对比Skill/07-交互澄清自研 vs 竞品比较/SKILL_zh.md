# 交互澄清自研 vs 竞品比较评测协议

本协议用于比较**同一 `case_id`（同题配对键）下**自研模型与一个竞品模型在交互澄清场景中的**整体链路 + 最终回答**。它沿用 `07-interactive-clarification` 的绝对评分体系（rubric、golden cases、root cause、tool list），并在此基础上增加 pairwise 比较协议与链路差异解释方法。

## 协议边界

- **绝对评分**：判断单个模型在交互澄清、多轮咨询、实体纠错、规则纠错和后续引导任务上答得好不好。
- **横向比较**：
  1. 对同题两边分别做绝对评分；
  2. 再比较自研强项、自研弱项和竞品强项；
  3. 最后用两边完整链路解释这些答案差异是怎么产生的。
- 比较对象不是“两个最终答案”这么窄，而是：
  - 同一用户问题；
  - 同一多轮上下文；
  - 两边最终回答，包括文本、图片、截图、表格截图或富媒体中的可见信息；
  - 两边可见整体链路，包括 `chain[*].plan`、`chain[*].tools[*]`、工具输入和工具输出。
- 链路的价值在于解释答案差异，不是脱离答案单独评判“工程美学”。

## 适用范围

仅在以下条件同时满足时使用本协议：
- 题目属于交互澄清、多轮咨询、投资对话承接、金融规则纠错、实体识别纠错、模糊条件口径化或答案后引导场景；
- 输入中存在同一 `case_id` 对应的两份记录；
- 两份记录分别代表自研模型与**一个**竞品模型；
- 当前任务目标是回答：
  - 自研模型相比竞品好在哪里；
  - 自研模型相比竞品差在哪里；
  - 竞品模型哪里值得学习。

适用题型包括：
- 用户意图模糊，需要主动澄清、口径化或给出分层方案：如“能帮我回本的股票”“平安现在能买吗”“主力高度控盘的个股”。
- 多轮咨询中用户补充了持仓、成本、股票、亏损幅度、时间目标、风险偏好等信息，需要承接前文而非重启回答。
- 用户问题包含错误前提或交易规则陷阱：做空、北交所权限、科创板盘后固定价格交易、撤单时间、T+1/T+0、分红除权除息、国债逆回购计息等。
- 用户输入包含错别字、拼音/同音误写、重复代码、股票代码多输一位、行业黑话或口语简称，需要识别最可能实体并在必要时澄清。
- 用户咨询金融术语、技术形态、策略条件或选股口径，需要把模糊词转成可核验定义。
- 答案应有后续引导、监控、提醒或继续追问，才能形成咨询闭环。

不适用于：
- 普通单模型质检；
- 不同问题之间的横向比较；
- 一次同时比较多个竞品模型；
- 普通事件资讯问答、纯回测取数计算、财报业绩归因、KYC 投顾适配、文档/图片问答或严格指令遵循；
- 只看最终答案、完全不需要链路归因的轻量 benchmark。

## 输入语义

每次评测至少读取：
- `case_id`：同题配对键（自研与竞品同 `case_id` 的记录对应同一问题）；
- 用户问题；
- `self_case_id`：自研记录唯一 ID；
- `competitor_case_id`：竞品记录唯一 ID；
- 自研模型完整记录；
- 竞品模型完整记录。

### 最终答案锚点

- 自研模型：优先使用 `text_answer` 作为最终答案主锚点；
- 竞品模型：若 `text_answer` 为空，则使用 `answer` 作为最终答案主锚点；
- 若最终答案包含图片、截图、图表、卡片或表格图片，必须读取其中可见文字和信息，把它们作为用户实际看到的答案内容共同评分；
- 若编排层已提前生成统一字段，可直接读取归一化后的最终答案，但不得因此改变原始证据指针。

### 真实链路结构

- `tool_usage` 是**评测维度名**，不是输入 JSON 的字段名；
- 真实工具调用从 `chain[N].tools[M]` 读取；
- 顶层 `tools` 字段即便存在，也可能为空，不能把它当成主要链路来源；
- 自研记录通常是多步 `chain`，`plan` 较完整；
- 竞品记录可能只有一个 `chain` step，`plan` 为空，但 `chain[0].tools` 仍包含可用的工具调用证据。

详细规则见：
- [references/comparison_protocol.md](references/comparison_protocol.md)
- [references/whole_chain_comparison.md](references/whole_chain_comparison.md)

## 执行协议

0. **先分析题目，建立共享评测框架**  
   阅读 [references/rubric/_index.md](references/rubric/_index.md)，仅依据用户问题判断维度适用性并分配动态权重。  
   同一题下，自研与竞品必须使用**同一套**适用性和权重，避免把权重差异误当成模型差异。  
   同时阅读 [references/golden_cases/_index.md](references/golden_cases/_index.md) 与 [references/golden_cases/image_annotation_anchors.md](references/golden_cases/image_annotation_anchors.md)，命中专家案例、同类语义或图片批注锚点时使用对应 hard checks。

1. **先分别做绝对评分**  
   对自研与竞品分别按本 skill 定义的 11 个维度评分：
   - `intent_fulfillment`
   - `ambiguity_clarification`
   - `context_continuity`
   - `entity_resolution`
   - `financial_rule_and_premise`
   - `assumption_definition`
   - `actionability_and_risk_plan`
   - `evidence_grounding`
   - `guidance_and_retention`
   - `tool_usage`
   - `latency_efficiency`

   仅对 `relevant` 和 `supplementary` 维度评分，跳过 `not_applicable` 维度。除 `tool_usage` 外，先只依据用户问题、共享上下文和各自最终答案评分；若最终答案包含图片、截图、图表、卡片或表格图片，必须读取其中可见文字和信息。不得因为另一方更差，就抬高本方绝对分。`latency_efficiency` 仅在存在 `timing` 或明确链路耗时证据时参与有效比较；无耗时证据时按补充维度给中性分并说明，不作为胜负核心依据。

2. **再分别诊断两边整体链路**  
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md)、[references/tool_list/_index.md](references/tool_list/_index.md) 和 [references/whole_chain_comparison.md](references/whole_chain_comparison.md)。  
   此时评分 `tool_usage`，并对两边分别检查：
   - 是否识别了用户真实咨询目标、信息缺口、错误前提和多轮上下文状态；
   - 是否正确处理错别字、同音、异常代码、简称和多义对象；
   - 是否正确核验交易规则、权限、税费、清算、计息和市场制度；
   - 工具选择是否正确，查询输入是否贴合任务；
   - 证据是否覆盖了题目真正需要的实体、规则、行情、公告、数据或图片信息；
   - 是否有必要交叉验证；
   - 工具结果是否真正转化成了更好的最终答案。

   当 `plan` 存在时，可结合其判断意图、澄清策略和推理；当 `plan` 为空时，不强行编造“推理文本”归因，优先依据工具行为、证据流和最终答案做判断。

3. **最后做 pairwise 比较**  
   阅读 [references/comparison_protocol.md](references/comparison_protocol.md)。  
   在双方绝对评分完成后，逐维比较：
   - 自研真正做得好的地方；
   - 自研真正落后的地方；
   - 竞品真正值得学习的地方；
   - 双方共同失败点；
   - 哪些链路差异导致了最终答案差异。

   比较时必须坚持：
   - **先绝对、后相对**：双方都差时，先写共同短板，再写谁相对更好；
   - **答案与链路合看**：答案决定质量，链路解释质量是怎么形成的；
   - **证据优先**：每条优势、弱点和学习点都要绑定最终答案或链路证据；
   - **不做多模型聚合**：本协议一次只比较一个竞品，跨竞品总结由后续汇总层完成。

4. **序列化输出**  
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。  
   先输出结构化 JSON，再附简短自然语言评审。

## 保守评分

- 自研与竞品使用同一维度、同一权重、同一 hard checks；
- 不因为相对胜负而改变绝对评分；
- 不要求 LLM 输出加权分、总分或最终分数；如后续汇总层需要，可由调用方基于 `scripts/rule.py` 权重另行计算；
- 不因为链路看起来繁复就自动加分；
- 若链路更好但最终答案没有兑现，优点只能记为链路信号，不能替代答案质量；
- 若双方都没有真正完成用户任务，必须明确输出共同不足，不能把“谁稍微好一点”写成高质量答案；
- `tool_usage` 在步骤 2 中依据链路评分，不在步骤 1 中盲评。

## 安全护栏

本 skill 沿用 `07-interactive-clarification` 的评分安全护栏，尤其包括：
- 交互澄清的核心不是“答得多”，而是先判断用户能不能被直接回答。用户缺成本、仓位、股票、目标价、风险偏好、时间范围或交易权限时，应该澄清、分层假设或明确口径。
- 首轮澄清只是开始。用户补充信息后，答案必须沿着前一轮建立的框架推进；若二轮完全重启、换题或忽略用户补充，要重扣 `context_continuity`。
- 金融交易规则陷阱必须先纠错。错误前提上继续给计划，是交互澄清类的硬伤，即使后续分析看起来专业也应触发封顶。
- 错别字和异常代码要贴近真实股民输入习惯。优先考虑 A 股常见标的、同音/近音、拼音习惯和问题语境；不能机械匹配到相似度更低或市场概率更低的实体。
- 模糊条件必须口径化。对“近期”“短线”“适中”“高度控盘”“回调较多”“业绩增长”等词，要给出筛选窗口、阈值、指标定义和局限。
- 对具体交易建议要可执行但不装确定。好答案应包括前提、触发条件、仓位/节奏、风险边界、观察指标和下一步补充信息，而不是只给一个价位或股票名单。
- 答案后引导不是泛泛“还有问题可以问我”，而是给出贴合当前咨询的下一步：同类标的监控、风险提醒、财报/分红日提醒、价格触发跟踪、候选池复查等。
- 速度可作为辅助扣分项；但不要让耗时掩盖事实错误、规则错误或承接断裂。
