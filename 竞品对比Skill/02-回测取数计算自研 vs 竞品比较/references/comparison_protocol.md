# 比较协议层

本文件只定义自研 vs 竞品的 pairwise 比较规则；绝对评分标准仍沿用原 02 skill。

## 比较顺序

1. 先确认同题：`case_id` 配对到同一问题，问题文本语义一致。
2. 先对自研与竞品分别做绝对评分。
3. 再比较双方差异。
4. 最后用链路证据解释差异来源。

## 先绝对、后相对

- 不得因为竞品更差，就把自研的绝对短板写成优势。
- 不得因为自研更差，就忽略竞品也没有达到专家标准。
- 若双方都未通过 hard checks，先写 `shared_failures`，再写相对优劣。
- 若双方都合格，再比较谁的数据更准、时间更稳、公式更对、明细更可复核、工具链路更能支撑答案。

## 输出对象的判定规则

### `self_strengths`

仅收录真正成立的我方优势：
- 相对竞品更强；
- 且本身也符合专家标准；
- 且有最终答案或链路证据支撑。

常见来源：
- 更准确识别用户的取数、统计、回测或盈亏计算意图；
- 更完整地覆盖股票、市场、日期、交易日、样本范围、指标字段和口径；
- 更正确地处理节假日、交易日、上市以来、过去 N 年、盘中时点等时间边界；
- 更准确地使用收益率、概率、毛利率、费用率、复权收益、组合盈亏等公式；
- 更清楚展示中间数据、样本明细、公式和最终计算过程；
- 更合理的工具组合被成功转化成答案质量和可复核性；
- 在有耗时证据时，以更低冗余完成同等或更高质量结果。

### `self_weaknesses`

收录自研相对竞品或相对专家标准的真实不足：
- 漏掉关键数据字段、样本范围或筛选条件；
- 时间窗口、交易日、节假日、披露日、盘中时点或复权口径处理不够准确；
- 公式、算术、分子分母、统计口径或单位换算有问题；
- 多步回测没有拆清楚条件发现、信号生成、买卖动作和收益计算；
- 答案缺少中间明细，导致结果不可验证；
- 工具链路虽复杂但没有兑现成更好的数据或计算结果；
- 有耗时证据时，存在明显冗余调用或响应效率问题。

### `competitor_strengths`

只写真正值得学习的地方：
- 竞品在答案中明显更好；
- 或竞品链路中出现了更优的数据获取、回测、计算、验证或效率策略，并最终改善了答案；
- 不能把“篇幅更长”“措辞更顺”或“模型名气更大”写成优势。

### `shared_failures`

双方都没达到专家标准时必须填写。典型情况：
- 都没有取到必要数据或样本严重不全；
- 都把自然日当交易日，或交易日/节假日边界错误；
- 都使用错误公式、错误复权口径、错误分子分母或错误单位；
- 都只给最终结论，没有明细和计算过程；
- 都没有处理用户明确要求的盘中精度、历史完整样本或多步策略条件；
- 都编造或输出无法验证的统计结果。

## 逐维比较

每个活跃维度都要回答三件事：
1. 谁更强 / 是否打平；
2. 差异体现在最终答案的什么地方；
3. 哪段链路证据最能解释这个差异。

推荐优先级：
- `intent_fulfillment`：先看谁真正完成了用户的取数计算任务；
- `data_retrieval_accuracy`：看谁的数据覆盖、字段、样本和来源更准确；
- `time_inference`：看谁的日期、交易日、节假日、时间窗口和精度更可靠；
- `calculation_accuracy`：看谁的公式、算术和口径更正确；
- `logical_decomposition`：看谁把复合任务拆成了可执行步骤；
- `result_verifiability`：看谁能让结果被复现和核验；
- `expression_quality`：看谁呈现更清楚，但不得压过正确性；
- `tool_usage`：看谁的工具选择、参数和证据编排更适合任务；

## 结论语义

- `absolute_summary`：先说双方各自好不好；
- `relative_summary`：再说谁相对更好；
- `verdict=self_better`：我方相对更好，且没有被双方共同失败掩盖；
- `verdict=competitor_better`：竞品相对更好；
- `verdict=tie`：双方接近；
- `verdict=both_poor`：双方都明显不达标，即便一方分数略高，也优先使用该结论。
