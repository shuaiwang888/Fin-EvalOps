# 回测取数计算评测协议

用稳定的协议评测我方自己的回测取数计算答案。以用户问题和我方最终答案（以 `text_answer` 为主锚点）为核心锚定绝对评分，规划链路主要用于根因归因；`tool_usage` 和 `latency_efficiency` 可按规则使用链路证据。

## 适用范围

仅在用户问题属于回测取数计算类任务时使用本协议，例如：
- 诊股查数：查询某只股票的历史价格、财务指标、涨停事件等
- 条件选股计算：按条件筛选股票并计算区间涨跌幅、概率等
- 历史统计：统计过去N年某行业/某月份的上涨概率、涨跌统计
- 财务指标提取与对比：从年报提取营收/成本/费用等指标，计算毛利率等衍生指标并与历史对比
- 组合盈亏计算：给定买入操作，计算到期盈亏金额
- 事件回测：涨停后次日表现、年报发布后涨跌幅、分红再投资收益等
- 多步条件回测：连续N日下跌后买入某指数的收益率等复合策略回测

不适用于事件/概念驱动选股、投资建议、市场评论或无计算/取数需求的纯行情查询。

## 期望输入

每次评测获取以下材料：
- 用户问题
- 我方最终答案
- 完整对话消息或规划链路
- 可用时提供响应耗时、工具调用时间戳或每步耗时

## 执行协议

0. **分析题目与分配动态权重**
   阅读 [references/rubric/_index.md](references/rubric/_index.md) 获取维度列表和适用性判断指南。
   仅阅读用户问题，对每个维度判断适用性：
   - `relevant`（核心相关）：该维度是本次评测的关键判断依据
   - `supplementary`（辅助相关）：该维度与题目有一定关联但非核心
   - `not_applicable`（不适用）：该维度与题目类型无关，跳过评分
   根据适用性分配动态权重（总和必须 = 100）：
   - `relevant` 维度获得较高权重（从 `not_applicable` 维度让出权重）
   - `supplementary` 维度保留低权重（建议 3-5）
   - `not_applicable` 维度权重 = 0，评分阶段直接跳过
   将权重分配记录到输出的 `weight_assignment` 中。
   阅读 [references/golden_cases/_index.md](references/golden_cases/_index.md)，判断用户问题是否命中专家案例或同类语义。命中时必须用对应 hard checks 作为核验清单。
1. **盲评打分**
   仅对 `relevant` 和 `supplementary` 维度评分，跳过 `not_applicable` 维度。
   依据用户问题和我方最终答案打分，忽略隐藏的规划过程。
   例外：`tool_usage` 维度需要阅读规划链路，在步骤 2 中评分；`latency_efficiency` 可以使用响应耗时、工具调用时间戳或链路耗时证据。
   `latency_efficiency` 在有耗时证据时评分；无耗时证据时给中性分并说明证据缺口。
   加权分 = raw_score / 100 × 动态权重。
2. **诊断根因**
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md) 获取归因规则，然后按需读取对应的 L1 文件。
   同时阅读 [references/tool_list/_index.md](references/tool_list/_index.md) 获取工具总览。
   此时评分 `tool_usage`：阅读规划链路并依据工具列表评估。
   仅从 `relevant` 和 `supplementary` 维度中选择根因，忽略 `not_applicable` 维度。
   按 raw_score 升序排列所有活跃维度（并列时按动态权重降序，再按维度名字母序）。
   得分最低的维度映射到最重要的根因。但如果触发的封顶规则上限较低，封顶违规维度驱动主要根因——因为它才是真正压低总分的原因。
   写一句 summary，将 L2 机制与该维度的失败模式融合。
   每个根因必须绑定证据——来自问题、最终答案、可见推理、工具调用、工具输出或耗时证据。
3. **应用封顶规则**
   所有维度评分完成后，按需读取 [references/rubric/](references/rubric/_index.md) 中对应的封顶规则文件。
   仅检查与 `relevant`/`supplementary` 维度相关的封顶规则。`not_applicable` 维度关联的封顶规则不触发。
   如果多条封顶规则同时触发，取最低的分数上限。
4. **序列化输出**
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。
   先输出结构化 JSON，再附简短的自然语言评审。

## 保守评分

使用以下评分规则：
- 仅对 `relevant` 和 `supplementary` 维度按六档原始分（0/20/40/60/80/100）打分，跳过 `not_applicable` 维度。
- **不要计算加权分、总分或最终分数**——这些由调用方代码自动计算。你只需输出每个维度的 `raw_score`（六档：0/20/40/60/80/100）和 `evidence`。
- 不要因为规划链路比最终答案更好而给隐藏加分。
- 例外：`tool_usage` 在步骤 2 中依据链路评分；`latency_efficiency` 可依据耗时证据评分。两者都不能给最终答案的事实、公式或意图错误补分。

## 安全护栏

遵循以下约束：
- 严肃对待时间推理。"节前N日"、"上市以来"、"过去X年"、"某年某月某日某时某分"等时间表达需要精确的交易日推算和时间范围定位。幻觉交易日状态（将交易日误判为非交易日）是严重错误。
- 严肃对待数据完整性。统计概率类查询需要足够的历史样本量。仅找到最近几个月的数据就做长期统计是不可接受的。
- 严肃对待计算公式。财务指标必须使用正确的专业公式（如毛利率、期间费用率、前复权价等），算术运算必须准确。
- 严肃对待多步拆解。复合条件查询（如"连续N日下跌后买入某指数"）需要正确拆解为可执行的子步骤，不能直接跳过或简化条件。
- 惩罚数据虚构。无法获取足够数据时应明确说明局限性，而非编造统计数据或伪造计算结果。编造金融统计数据对投资者的风险远大于数据不完整。
- 单独惩罚日内精度缺失。用户要求某时某分或开盘/盘中精度时，用日线数据给确定金额属于严重锚点错误；若只能估算，必须明确声明限制。
- 记录执行效率。大规模统计和复杂回测如果耗时显著过长且结果仍错，应同时暴露效率问题和正确性问题。
