# 事件与概念选股评测协议

用稳定的协议评测我方自己的事件/概念驱动选股答案。以用户问题和我方最终答案（以 `text_answer` 为主锚点）为核心锚定绝对评分，规划链路仅用于根因归因。

## 适用范围

仅在用户问题属于事件/概念驱动的选股或排序任务时使用本协议，例如：
- 哪些股票最受益于某次战争、政策、产品发布、供给冲击或地缘事件
- 哪些概念股可能领涨、爆发或排名第一
- 某主题的核心受益标的 vs 边缘受益标的是哪些
- 哪些事件驱动目标最值得关注及其原因
- 某产业链、材料、设备、客户供货、主营产品或产能份额对应哪些 A 股标的
- 美股/海外巨头/产业标杆映射到国内沪深股市的可比公司
- 主题交集、概念板块、政策方向下的主线拆解、梯队划分和核心个股识别

不适用于普通行情查询、个股诊断、投资组合建议或无事件/主题推理层的纯条件筛选。

**与 08-资讯知识问答的边界：** 若用户问题的最终落点是"选出/排序受益标的"，用 01；若最终落点是"解释事件本身、影响链条或异动原因"（不以选股排序为结论），用 08。当两者都涉及受益标的时，优先看答案结构：以个股列表、排序、梯队划分为核心输出的归 01，以事件梳理、影响分析、行业判断为主线、个股仅作附带提及的归 08。

**与 06-复合意图的边界：** 若问题仅围绕单一事件/概念驱动选股（一个事件→一组标的），用 01；若问题包含多个子任务、跨多源信息整合（如同时要求行情+新闻+财务+策略+估值），或需要拆解、推演并输出决策闭环，用 06。简单产业链映射（某材料/设备/客户对应哪些标的）归 01，多环节产业链深度调研或竞争格局分析归 06。

## 期望输入

每次评测获取以下材料：
- 用户问题
- 我方最终答案
- 完整对话消息或规划链路

## 执行协议

0. **分析题目与分配动态权重**
   阅读 [references/rubric/_index.md](references/rubric/_index.md) 获取维度列表和适用性判断指南。
   仅阅读用户问题，对每个维度判断适用性：
   - `relevant`（核心相关）：该维度是本次评测的关键判断依据
   - `supplementary`（辅助相关）：该维度与题目有一定关联但非核心
   - `not_applicable`（不适用）：该维度与题目类型无关，跳过评分
   根据适用性分配动态权重（总和必须 = 100）：
   - `relevant` 维度获得较高权重（从 `not_applicable` 维度让出权重）
   - `supplementary` 维度保留低权重（建议 3-5）
   - `not_applicable` 维度权重 = 0，评分阶段直接跳过
   将权重分配记录到输出的 `weight_assignment` 中。
   阅读 [references/golden_cases/_index.md](references/golden_cases/_index.md)，判断用户问题是否命中专家案例或同类语义。命中时必须用对应 hard checks 作为核验清单；未命中具体案例时，也要使用文件末尾的跨案例判分锚点。
   同时阅读 [references/golden_cases/image_annotation_anchors.md](references/golden_cases/image_annotation_anchors.md)，使用图片人工批注中的补充锚点核验图表、排序、交易性价比、非标产业证据和实体边界问题。
1. **盲评打分**
   仅对 `relevant` 和 `supplementary` 维度评分，跳过 `not_applicable` 维度。
   依据用户问题和我方最终答案打分，忽略隐藏的规划过程。
   例外：`tool_usage` 维度需要阅读规划链路，在步骤 2 中评分。
   仅输出 raw_score（0/20/40/60/80/100 六档整数），加权分和总分由调用方代码自动计算。
2. **诊断根因**
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md) 获取归因规则，然后按需读取对应的 L1 文件。
   同时阅读 [references/tool_list/_index.md](references/tool_list/_index.md) 获取工具总览。
   此时评分 `tool_usage`：阅读规划链路并依据工具列表评估。
   注意：当前可用工具包括 Search、FinQuery、BackTest、Forecast、AccessingFullText、SearchImage、CustomerServiceFAQ、SaveUserProfile、CodeInterpreter。
   仅从 `relevant` 和 `supplementary` 维度中选择根因，忽略 `not_applicable` 维度。
   在归因前，先评估是否有封顶规则可能被触发（详见步骤 3 的封顶条件），以便在选择主要根因时判断"封顶违规维度是否比最低分维度更能解释得分下降"。
   按 raw_score 升序排列所有活跃维度（并列时按 weight_assignment 中的 dynamic_weight 降序，再按维度名字母序）。
   得分最低的维度映射到最重要的根因。但如果触发的封顶规则上限较低，封顶违规维度驱动主要根因——因为它才是真正压低总分的原因。
   写一句 summary，将 L2 机制与该维度的失败模式融合。
   每个根因必须绑定证据——来自问题、最终答案、可见推理、工具调用或工具输出。
3. **应用封顶规则**
   所有维度评分完成后，按需读取 [references/rubric/](references/rubric/_index.md) 中对应的封顶规则文件。
   仅检查与 `relevant`/`supplementary` 维度相关的封顶规则。`not_applicable` 维度关联的封顶规则不触发。
   如果多条封顶规则同时触发，取最低的分数上限。
4. **序列化输出**
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。
   先输出结构化 JSON，再附简短的自然语言评审。

## 保守评分

使用以下评分规则：
- 仅对 `relevant` 和 `supplementary` 维度按 0/20/40/60/80/100 六档原始分打分，跳过 `not_applicable` 维度。
- **不要计算加权分、总分或最终分数**——这些由调用方代码自动计算。你只需输出每个维度的 `raw_score`（0/20/40/60/80/100 六档整数）和 `evidence`。
- 不要因为规划链路比最终答案更好而给隐藏加分。
- 例外：`tool_usage` 在步骤 2 中依据链路评分，不在步骤 1 中盲评。

## 安全护栏

遵循以下约束：
- 严肃对待隐含意图。"最受益"、"领涨"、"最相关"或"排序"类问题需要优先级判断和理由，而非概念罗列。
- 严肃对待时间范围。包含"最新"、"最近"、"截至某日"、"近两天"或明确日期的问题需要严格的时间边界检查。
- 严肃对待证据类型。如果用户要新闻或事件触发因素，不要将通用报告或宽泛的概念简介等同为事件/新闻依据。
- 惩罚数据堆砌。没有投资论点、排序逻辑或受益推理的表格不是好答案。
- 惩罚"只会取数"。事件/主题选股的核心不是把概念成分股倒出来，而是完成概念脱水、受益纯度划分、核心标的提炼和可执行排序。
- 要求硬证据支撑。产能最高、订单多、市占率高、供货给某客户、成本低、现金流强、技术强、对标海外巨头等断言，必须有量化指标、业务口径或来源类型支撑。
- 区分直接与间接关联。必须识别主营/副业、直接供货/间接供应链、核心产品/边缘材料、品牌厂/代工厂、上游材料/下游应用等边界。
- 对映射和类比保持克制。A 股对标美股或海外巨头时，允许明确"没有完全对标"，但必须拆解业务模式、收入来源、技术壁垒和产业位置；强行凑相似会严重扣分。
- 不要让行情指标压倒事件相关度。事件炒作通常先看事件贴合度和受益纯度，再看资金流、弹性、换手和涨幅等交易指标。
