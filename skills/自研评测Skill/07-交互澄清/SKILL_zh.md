# 交互澄清评测协议

用稳定协议评测问财模型在交互澄清场景中的表现。以用户问题和最终答案 `text_answer` 为评分主锚点，以完整上下文和链路数据用于多轮承接、工具评分、效率判断和根因归因。

## 适用范围

仅在用户问题属于交互澄清、多轮咨询或投资对话承接时使用，包括：
- 用户意图模糊，需要主动澄清、口径化或给出分层方案：如"能帮我回本的股票""平安现在能买吗""主力高度控盘的个股"。
- 多轮咨询中用户补充了持仓、成本、股票、亏损幅度、时间目标、风险偏好等信息，需要承接前文而非重启回答。
- 用户问题包含错误前提或交易规则陷阱：做空、北交所权限、科创板盘后固定价格交易、撤单时间、T+1/T+0、分红除权除息、国债逆回购计息等。
- 用户输入包含错别字、拼音/同音误写、重复代码、股票代码多输一位、行业黑话或口语简称，需要识别最可能实体并在必要时澄清。
- 用户咨询金融术语、技术形态、策略条件或选股口径，需要把模糊词转成可核验定义：如"短线""近期""回调比较多""业绩还在增长""现金奶牛""净利润断层"。
- 答案应有后续引导、监控、提醒或继续追问，才能形成咨询闭环。

不适用于普通事件资讯问答、纯回测取数计算、财报业绩归因、KYC 投顾适配、文档/图片问答或严格指令遵循；这些分别使用对应 skill。若问题核心是"最新政策/新闻/事件影响"，优先使用资讯知识问答类 skill；若问题核心是"诊股查数"，优先使用诊股查数 skill。

## 期望输入

每次评测获取：
- 用户问题 `question`
- 我方最终答案，优先使用 `text_answer`
- 完整对话上下文 `context`，包含历史轮次的用户补充和模型承诺
- 完整规划链路 `chain`，包括 `plan`、工具调用、工具输入和工具输出
- 可用工具清单 `tools`
- 可选响应耗时、工具调用耗时或时间戳 `timing`
- 可选人工复核反馈、线上维度统计或新增失败样本 `online_dimension_signals`

## 执行协议

0. **分析题目与分配动态权重**  
   阅读 [references/rubric/_index.md](references/rubric/_index.md) 和 [references/golden_cases/_index.md](references/golden_cases/_index.md)。仅根据用户问题判断每个维度适用性：`relevant` / `supplementary` / `not_applicable`。动态权重总和必须为 100，并写入 `weight_assignment`。命中专家案例或同类语义时，必须使用对应 hard checks；未命中具体案例时，也要使用 golden cases 文件末尾的跨案例判分锚点。  
   如果题目涉及截图批注、模型答复高亮、上下文承接、首轮澄清和二轮落地差异，再阅读 [references/golden_cases/image_annotation_anchors.md](references/golden_cases/image_annotation_anchors.md)。

1. **盲评最终答案**  
   以 `text_answer` 为主锚点评分，不因为隐藏链路更好而给最终答案加分。对所有活跃维度输出 `raw_score`（六档：0/20/40/60/80/100）和 `evidence`；不要计算加权分、总分或最终分数。`tool_usage` 例外，在步骤 2 评分；`latency_efficiency` 可依据 `timing` 或链路耗时证据评分，无耗时证据时给中性分并说明。

2. **链路诊断和根因归因**  
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md)，再阅读 [references/tool_list/_index.md](references/tool_list/_index.md)。用 `context` 和 `chain.plan` 判断意图理解、澄清策略、错误前提识别和多轮承接；用 `chain.tools[*].input/output` 判断实体识别、交易规则核验、结构化数据查询、搜索/公告/规则来源和交叉验证。此时评分 `tool_usage`。根因必须绑定证据。

3. **应用封顶规则**  
   按需读取 [references/rubric/](references/rubric/_index.md) 中的 `cap_*.md` 文件。封顶规则限制最终分，不替代维度评分。多个封顶同时触发时取最低上限。

4. **序列化输出**  
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。先输出结构化 JSON，再附简短自然语言评审。

## 保守评分

- 交互澄清的核心不是"答得多"，而是先判断用户能不能被直接回答。用户缺成本、仓位、股票、目标价、风险偏好、时间范围或交易权限时，应该澄清、分层假设或明确口径。
- 首轮澄清只是开始。用户补充信息后，答案必须沿着前一轮建立的框架推进；若二轮完全重启、换题或忽略用户补充，要重扣 `context_continuity`。
- 金融交易规则陷阱必须先纠错。错误前提上继续给计划，是交互澄清类的硬伤，即使后续分析看起来专业也应触发封顶。
- 错别字和异常代码要贴近真实股民输入习惯。优先考虑 A 股常见标的、同音/近音、拼音习惯和问题语境；不能机械匹配到相似度更低或市场概率更低的实体。
- 模糊条件必须口径化。对"近期""短线""适中""高度控盘""回调较多""业绩增长"等词，要给出筛选窗口、阈值、指标定义和局限。
- 对具体交易建议要可执行但不装确定。好答案应包括前提、触发条件、仓位/节奏、风险边界、观察指标和下一步补充信息，而不是只给一个价位或股票名单。
- 答案后引导不是泛泛"还有问题可以问我"，而是给出贴合当前咨询的下一步：同类标的监控、风险提醒、财报/分红日提醒、价格触发跟踪、候选池复查等。
- 速度可作为辅助扣分项。专家数据中该场景问财质量和速度双低；但不要让耗时掩盖事实错误、规则错误或承接断裂。
