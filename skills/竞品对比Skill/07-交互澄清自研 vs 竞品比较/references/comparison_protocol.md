# 比较协议层

本文件只定义自研 vs 竞品的 pairwise 比较规则；绝对评分标准由本 skill 的 rubric 体系定义。比较时不得修改 `07-interactive-clarification` 的维度、权重逻辑、封顶规则或根因分类。

## 比较顺序

1. 先确认同题：`self_case_id + competitor_case_id` 配对到同一问题，问题文本和上下文语义一致。
2. 先对自研与竞品分别做绝对评分。
3. 再比较双方差异。
4. 最后用链路证据解释差异来源。

## 先绝对、后相对

- 不得因为竞品更差，就把自研的绝对短板写成优势。
- 不得因为自研更差，就忽略竞品也没有达到专家标准。
- 若双方都未通过 hard checks，先写 `shared_failures`，再写相对优劣。
- 若双方都合格，再比较谁更完整、谁更有咨询价值、谁更值得学习。

## 输出对象的判定规则

### `self_strengths`

仅收录真正成立的我方优势：
- 相对竞品更强；
- 且本身也符合专家标准；
- 且有最终答案或链路证据支撑。

常见来源：
- 更准确识别信息缺口并提出关键澄清；
- 用户补充后更好承接前轮框架；
- 更贴近真实股民输入习惯完成实体纠错；
- 更准确处理交易规则、权限、税费、计息和错误前提；
- 更能把模糊条件转成可核验口径；
- 更能给出有条件、有风险边界、可跟踪的后续动作；
- 更合理的工具组合被成功转化成答案质量。

### `self_weaknesses`

收录自研相对竞品或相对专家标准的真实不足：
- 应澄清却直接下结论；
- 多轮承接断裂；
- 错别字、异常代码或简称识别错误；
- 交易规则或权限判断错误；
- 模糊口径没有定义清楚；
- 给出具体操作建议但缺证据、缺风险边界；
- 工具链路虽复杂但没有兑现成更好的结论。

### `competitor_strengths`

只写真正值得学习的地方：
- 竞品在答案中明显更好；
- 或竞品链路中出现了更优的澄清、实体核验、规则核验、证据获取或持续服务策略，并最终改善了答案；
- 不能把“篇幅更长”“措辞更顺”或“模型名气更大”写成优势。

### `shared_failures`

双方都没达到专家标准时必须填写。典型情况：
- 都没有识别必须澄清的关键变量；
- 都忽略用户补充信息；
- 都没有纠正错误交易前提；
- 都识别错标的或实体边界；
- 都输出模板化建议，没有形成咨询闭环；
- 都给出缺证据的具体交易建议。

## 逐维比较

每个活跃维度都要回答三件事：
1. 谁更强 / 是否打平；
2. 差异体现在最终答案的什么地方；
3. 哪段链路证据最能解释这个差异。

推荐优先级：
- `intent_fulfillment`：先看谁真正完成了用户咨询目标；
- `ambiguity_clarification`：看谁更准确判断“能否直接回答”；
- `context_continuity`：看谁更好承接历史轮次和用户补充；
- `entity_resolution`：看谁更稳健处理错别字、代码异常和简称；
- `financial_rule_and_premise`：看谁更准确纠正规则和错误前提；
- `assumption_definition`：看谁把模糊口径定义得更可核验；
- `actionability_and_risk_plan`：看谁的下一步更可执行且风险边界清楚；
- `evidence_grounding`：看谁的事实、规则、行情或公告证据更能支撑结论；
- `guidance_and_retention`：看谁形成更贴题的后续服务闭环；
- `tool_usage`：看谁的工具选择和证据编排更适合任务；
- `latency_efficiency`：看谁在质量达标前提下链路更高效。

## 结论语义

- `absolute_summary`：先说双方各自好不好；
- `relative_summary`：再说谁相对更好；
- `verdict=self_better`：我方相对更好，且没有被双方共同失败掩盖；
- `verdict=competitor_better`：竞品相对更好；
- `verdict=tie`：双方接近；
- `verdict=both_poor`：双方都明显不达标，即便一方分数略高，也优先使用该结论。
