# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- 若最终答案包含图片、截图、卡片或表格图片，需要读取其中可见文字和信息。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量答案：

1. **意图与澄清策略**
   - 是否识别用户不能被直接回答的关键缺口；
   - 是否区分必须追问、可假设分层和可直接给临时方案的情况；
   - 是否在用户补充后沿前轮澄清框架推进。

2. **实体与规则核验**
   - 错别字、同音、异常代码、简称是否通过合适工具或上下文确认；
   - 交易规则、权限、撤单、T+1、分红、国债逆回购等问题是否使用可靠来源核验；
   - 是否避免在错误前提上继续给操作方案。

3. **工具选择与查询设计**
   - 规则和公告是否用 Search / CustomerServiceFAQ / AccessingFullText 等工具核验；
   - 结构化行情、标的、财务、资金和筛选条件是否用 FinQuery 等工具确认；
   - 查询词、参数、时间窗和候选实体是否贴合任务；
   - 是否避免用宽泛查询替代关键变量核验。

4. **证据覆盖与交叉验证**
   - 是否同时覆盖用户目标、实体、规则、行情、风险和后续动作所需证据；
   - 是否在工具结果之间做交叉核验；
   - 是否处理冲突口径，而不是机械拼接。

5. **证据向答案的转化**
   - 查到的数据是否真正支撑了澄清问题、规则纠错、行动方案和后续引导；
   - 是否存在“链路里查得不错，答案里却没有兑现”的断层；
   - 是否存在“工具很多，但仍然输出模板化建议”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 -> 答案结果”的形式：
- 因为自研先识别缺少成本、仓位和时间目标，所以最终没有直接给误导性的回本承诺；
- 因为竞品核验了北交所权限和交易规则，所以最终避免了不可执行方案；
- 因为自研虽然查到了行情数据，但没有把用户补充的成本价纳入方案，所以 `context_continuity` 和 `actionability_and_risk_plan` 仍然失分；
- 因为竞品 `plan` 不可见，但其 `chain[0].tools` 覆盖了规则来源和标的核验，所以可把规则准确性归因到工具证据。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把链路中的好信号直接当成最终答案优势，除非它已经转化为用户可见答案质量。
