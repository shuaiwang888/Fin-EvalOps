# 回测取数计算自研 vs 竞品比较评测协议

本协议用于比较**同一 `case_id`（同题配对键）下**自研模型与一个竞品模型的**整体链路 + 最终回答**。它定义了回测取数计算领域的绝对评分体系（由 rubric、golden cases、root cause 构成），以及 pairwise 比较协议与链路差异解释方法。

## 协议边界

- **绝对评分**：判断单个模型在回测取数计算任务上答得好不好。
- **横向比较**：
  1. 对同题两边分别做绝对评分；
  2. 再比较自研强项、自研弱项和竞品强项；
  3. 最后用两边完整链路解释这些答案差异是怎么产生的。
- 比较对象不是“两个最终答案”这么窄，而是：
  - 同一用户问题；
  - 两边最终回答；
  - 两边可见整体链路，包括 `chain[*].plan`、`chain[*].tools[*]`、工具输入、工具输出，以及可用的耗时证据。
- 链路的价值在于解释答案差异，不是脱离答案单独评判“工程美学”。回测取数计算类任务最终以**数据是否取对、时间是否推对、公式是否算对、结果是否可复核**为核心。

## 适用范围

仅在以下条件同时满足时使用本协议：
- 题目属于回测取数计算类任务，例如历史价格/财务指标提取、区间涨跌幅、历史概率统计、事件回测、组合盈亏、多步条件回测等；
- 输入中存在同一 `case_id` 对应的两份记录；
- 两份记录分别代表自研模型与**一个**竞品模型；
- 当前任务目标是回答：
  - 自研模型相比竞品好在哪里；
  - 自研模型相比竞品差在哪里；
  - 竞品模型哪里值得学习。

不适用于：
- 普通单模型质检；
- 不同问题之间的横向比较；
- 一次同时比较多个竞品模型；
- 事件/概念驱动选股、投资建议、市场评论或无计算/取数需求的纯行情查询；
- 只看最终答案、完全不需要链路归因的轻量 benchmark。

## 输入语义

每次评测至少读取：
- `case_id`：同题配对键；
- 用户问题；
- 自研模型完整记录；
- 竞品模型完整记录。

### 最终答案锚点

- 自研模型：优先使用 `text_answer` 作为最终答案主锚点；
- 竞品模型：若 `text_answer` 为空，则使用 `answer` 作为最终答案主锚点；
- 若编排层已提前生成统一字段，可直接读取归一化后的最终答案，但不得因此改变原始证据指针。

### 真实链路结构

- `tool_usage` 是**评测维度名**，不是输入 JSON 的字段名；
- 真实工具调用从 `chain[N].tools[M]` 读取；
- 顶层 `tools` 字段即便存在，也可能为空，不能把它当成主要链路来源；
- 自研记录通常是多步 `chain`，`plan` 较完整；
- 竞品记录可能只有一个 `chain` step，`plan` 为空，但 `chain[0].tools` 仍包含可用的工具调用证据；
详细规则见：
- [references/comparison_protocol.md](references/comparison_protocol.md)
- [references/whole_chain_comparison.md](references/whole_chain_comparison.md)

## 执行协议

0. **先分析题目，建立共享评测框架**
   阅读 [references/rubric/_index.md](references/rubric/_index.md)，仅依据用户问题判断维度适用性并分配动态权重。
   同一题下，自研与竞品必须使用**同一套**适用性和权重，避免把权重差异误当成模型差异。
   同时阅读 [references/golden_cases/_index.md](references/golden_cases/_index.md)，命中专家案例时使用对应 hard checks。

1. **先分别做绝对评分**
   对自研与竞品分别按本 skill 定义的 8 个维度评分：
   - `intent_fulfillment`
   - `data_retrieval_accuracy`
   - `time_inference`
   - `calculation_accuracy`
   - `logical_decomposition`
   - `result_verifiability`
   - `expression_quality`
   - `tool_usage`

   仅对 `relevant` 和 `supplementary` 维度评分，跳过 `not_applicable` 维度。除 `tool_usage` 外，先只依据用户问题和各自最终答案评分；不得因为另一方更差，就抬高本方绝对分。

2. **再分别诊断两边整体链路**
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md)、[references/tool_list/_index.md](references/tool_list/_index.md) 和 [references/whole_chain_comparison.md](references/whole_chain_comparison.md)。
   对两边分别检查：
   - 任务是否被正确拆解为取数、时间推理、计算、验证和呈现步骤；
   - 工具选择是否正确，例如结构化行情/财务数据、回测统计、全文公告、搜索、代码计算是否各司其职；
   - 查询输入是否贴合股票、日期、交易日、复权口径、指标字段、样本范围和统计口径；
   - 证据是否覆盖了题目真正需要的数据明细、样本量、公式和中间过程；
   - 工具结果是否真正转化成了更准确、可复核的最终答案。

   当 `plan` 存在时，可结合其判断意图、拆解和计算推理；当 `plan` 为空时，不强行编造“推理文本”归因，优先依据工具行为、证据流、计算结果和最终答案做判断。

3. **最后做 pairwise 比较**
   阅读 [references/comparison_protocol.md](references/comparison_protocol.md)。
   在双方绝对评分完成后，逐维比较：
   - 自研真正做得好的地方；
   - 自研真正落后的地方；
   - 竞品真正值得学习的地方；
   - 双方共同失败点；
   - 哪些链路差异导致了最终答案差异。

   比较时必须坚持：
   - **先绝对、后相对**：双方都差时，先写共同短板，再写谁相对更好；
   - **答案与链路合看**：答案决定质量，链路解释质量是怎么形成的；
   - **计算正确性优先**：数据、时间、公式、口径任一核心环节错误，都不能被流畅表达或复杂链路掩盖；
   - **证据优先**：每条优势、弱点和学习点都要绑定最终答案或链路证据；
   - **不做多模型聚合**：本协议一次只比较一个竞品，跨竞品总结由后续汇总层完成。

4. **序列化输出**
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。
   先输出结构化 JSON，再附简短自然语言评审。

## 保守评分

- 自研与竞品使用同一维度、同一权重、同一 hard checks；
- 不因为相对胜负而改变绝对评分；
- 不因为链路看起来繁复就自动加分；
- 若链路更好但最终答案没有兑现，优点只能记为链路信号，不能替代答案质量；
- 若答案给错了核心数据、时间窗口、交易日、公式或统计口径，即便表达更完整也必须扣分并按需触发封顶规则；
- 若双方都没有真正完成用户任务，必须明确输出共同不足，不能把“谁稍微好一点”写成高质量答案。

## 安全护栏

本 skill 的评分安全护栏，尤其包括：
- 严肃对待时间推理。“节前 N 日”“上市以来”“过去 X 年”“某年某月某日某时某分”等时间表达需要精确的交易日推算和时间范围定位；
- 严肃对待数据完整性。统计概率类查询需要足够历史样本量，不能用少量样本冒充长期统计；
- 严肃对待计算公式。财务指标、收益率、概率、盈亏和复权收益必须使用正确专业公式；
- 严肃对待多步拆解。复合策略回测必须拆成条件发现、信号生成、交易执行、收益计算；
- 惩罚数据虚构。无法获取足够数据时应明确说明局限性，而非编造统计数据或伪造计算结果；
- 单独惩罚日内精度缺失。用户要求某时某分或开盘/盘中精度时，用日线数据给确定金额属于严重锚点错误；
