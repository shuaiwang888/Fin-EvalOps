# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出、计算结果和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量答案：

1. **任务拆解**
   - 是否识别出题目要求的是取数、统计、回测、财务指标提取、组合盈亏还是事件后表现；
   - 是否把复合任务拆成条件发现、样本构建、时间锚定、交易动作、收益/概率计算和结果验证；
   - 是否避免把多步策略简化成单次查询。

2. **工具选择**
   - 结构化行情、财务和指标数据是否使用 FinQuery 等合适工具；
   - 历史统计、事件回测和策略收益是否使用 BackTest 或等价可复现工具；
   - 需要公告、年报、披露日或原文证据时是否补足 Search / AccessingFullText；
   - 需要复杂计算、清洗或表格汇总时是否合理使用 CodeInterpreter；
   - 是否存在该用工具而未用、工具选错、重复调用或参数明显错误。

3. **查询设计**
   - 查询参数是否精确覆盖股票/代码、市场范围、日期、交易日、盘中时点、复权口径、指标字段、样本窗口和筛选条件；
   - 是否处理“上市以来”“过去 N 年”“节前 N 日”“年报发布次日”等高风险时间表达；
   - 是否避免用过宽泛或错误类型的数据替代关键证据。

4. **证据覆盖与交叉验证**
   - 是否给出原始数据、样本量、明细列表、中间表、公式和计算过程；
   - 是否在行情、公告、财务、回测结果之间做必要核验；
   - 是否处理了冲突口径，而不是机械拼接。

5. **证据向答案的转化**
   - 查到的数据是否真正支撑了最终数值、概率、盈亏、排序或结论；
   - 是否存在“链路里查得不错，答案里却算错/漏写/不可验证”的断层；
   - 是否存在“工具很多，但仍然只输出不可复核结论”的伪复杂。

## 如何解释答案差异

优先写成“链路动作 → 答案结果”的形式：
- 因为自研先确定节前 5 个交易日，再做全市场筛选，所以最终时间窗口和样本覆盖更可靠；
- 因为竞品直接用自然日区间取数，没有校验交易日，所以后续涨跌幅计算整体偏离；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了回测明细和样本表，所以最终概率结果更可验证；
- 因为自研调用了财务字段却没有把营业成本、费用项代入正确公式，所以链路信号不能抵消计算错误。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了数据、计算和可复核性；
- 不用表达流畅掩盖核心数据、时间、公式或口径错误；
