# 诊股查数自研 vs 竞品比较评测协议

本协议用于比较**同一 `case_id`（同题配对键）下**自研模型与一个竞品模型的**整体链路 + 最终回答**。它定义了诊股查数领域的绝对评分体系（由 rubric、golden cases、root cause 构成），以及 pairwise 比较协议与链路差异解释方法。

## 协议边界

- **绝对评分**：判断单个模型在诊股查数、个股/板块数据查询、对比分析或轻量诊断任务上答得好不好。
- **横向比较**：
  1. 对同题两边分别做绝对评分；
  2. 再比较自研强项、自研弱项和竞品强项；
  3. 最后用两边完整链路解释这些答案差异是怎么产生的。
- 比较对象不是“两个最终答案”这么窄，而是：
  - 同一用户问题；
  - 两边最终回答；
  - 两边可见整体链路，包括 `chain[*].plan`、`chain[*].tools[*]`、工具输入、工具输出，以及可用的耗时证据。
- 链路的价值在于解释答案差异，不是脱离答案单独评判“工程美学”。诊股查数类任务最终以**数据准确、时间口径清楚、分析框架匹配、结果可复核、洞察有增量**为核心。

## 适用范围

仅在以下条件同时满足时使用本协议：
- 题目属于诊股查数、个股/板块数据查询、多标的对比、跨市场/跨品种数据、宏观金融数据、全市场条件查询或轻量诊断任务；
- 输入中存在同一 `case_id` 对应的两份记录；
- 两份记录分别代表自研模型与**一个**竞品模型；
- 当前任务目标是回答：
  - 自研模型相比竞品好在哪里；
  - 自研模型相比竞品差在哪里；
  - 竞品模型哪里值得学习。

不适用于：
- 普通单模型质检；
- 不同问题之间的横向比较；
- 一次同时比较多个竞品模型；
- 事件/概念驱动选股、重度投顾推荐、KYC 适配建议、纯财报业绩归因、复杂策略回测或客服问答；
- 只看最终答案、完全不需要链路归因的轻量 benchmark。

## 输入语义

每次评测至少读取：
- `case_id`：同题配对键；
- 用户问题；
- 自研模型完整记录；
- 竞品模型完整记录。

### 最终答案锚点

- 自研模型：优先使用 `text_answer` 作为最终答案主锚点；
- 竞品模型：若 `text_answer` 为空，则使用 `answer` 作为最终答案主锚点；
- 若编排层已提前生成统一字段，可直接读取归一化后的最终答案，但不得因此改变原始证据指针。

### 真实链路结构

- `tool_usage` 是**评测维度名**，不是输入 JSON 的字段名；
- 真实工具调用从 `chain[N].tools[M]` 读取；
- 顶层 `tools` 字段即便存在，也可能为空，不能把它当成主要链路来源；
- 自研记录通常是多步 `chain`，`plan` 较完整；
- 竞品记录可能只有一个 `chain` step，`plan` 为空，但 `chain[0].tools` 仍包含可用的工具调用证据；
详细规则见：
- [references/comparison_protocol.md](references/comparison_protocol.md)
- [references/whole_chain_comparison.md](references/whole_chain_comparison.md)

## 执行协议

0. **先分析题目，建立共享评测框架**
   阅读 [references/rubric/_index.md](references/rubric/_index.md)，仅依据用户问题判断维度适用性并分配动态权重。
   同一题下，自研与竞品必须使用**同一套**适用性和权重，避免把权重差异误当成模型差异。
   同时阅读 [references/golden_cases/_index.md](references/golden_cases/_index.md)，命中专家案例或同类语义时使用对应 hard checks；题目涉及图表、截图、可视化对比、多周期展示或工具失败归因时，再读取 [references/golden_cases/image_annotation_anchors.md](references/golden_cases/image_annotation_anchors.md)。

1. **先分别做绝对评分**
   对自研与竞品分别按本 skill 定义的 9 个维度评分：
   - `intent_fulfillment`
   - `data_accuracy_coverage`
   - `time_caliber_precision`
   - `calculation_comparison`
   - `analysis_framework_fit`
   - `insight_extension`
   - `result_verifiability`
   - `presentation_visualization`
   - `tool_usage`

   仅对 `relevant` 和 `supplementary` 维度评分，跳过 `not_applicable` 维度。`tool_usage` 在步骤 2 链路诊断阶段才评分，本步骤不评分。先只依据用户问题和各自最终答案评分；不得因为另一方更差，就抬高本方绝对分。

2. **再分别诊断两边整体链路**
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md)、[references/tool_list/_index.md](references/tool_list/_index.md) 和 [references/whole_chain_comparison.md](references/whole_chain_comparison.md)。
   对两边分别检查：
   - 是否识别用户真实诊股/查数意图和隐含金融语义；
   - 工具选择是否正确，例如结构化行情/财务数据、分时数据、资金流、龙虎榜、搜索、公告、研报、调研纪要、跨市场品种和汇率数据是否各司其职；
   - 查询输入是否贴合标的、市场、行业、年份、日期、交易日、复权、合约、单位、汇率、筛选条件和样本范围；
   - 证据是否覆盖用户真正需要的数据、口径、对比、分析框架、增量信息和可验证明细；
   - 工具结果是否真正转化成了更准确、更有诊断价值、更可复核的最终答案。

   当 `plan` 存在时，可结合其判断意图理解、金融分析框架和推理过程；当 `plan` 为空时，不强行编造“推理文本”归因，优先依据工具行为、证据流、数据口径、最终答案做判断。

3. **最后做 pairwise 比较**
   阅读 [references/comparison_protocol.md](references/comparison_protocol.md)。
   在双方绝对评分完成后，逐维比较：
   - 自研真正做得好的地方；
   - 自研真正落后的地方；
   - 竞品真正值得学习的地方；
   - 双方共同失败点；
   - 哪些链路差异导致了最终答案差异。

   比较时必须坚持：
   - **先绝对、后相对**：双方都差时，先写共同短板，再写谁相对更好；
   - **答案与链路合看**：答案决定质量，链路解释质量是怎么形成的；
   - **诊股查数核心优先**：数据、时间口径、分析框架、关键明细任一核心环节错误，都不能被流畅表达或复杂链路掩盖；
   - **证据优先**：每条优势、弱点和学习点都要绑定最终答案或链路证据；
   - **不做多模型聚合**：本协议一次只比较一个竞品，跨竞品总结由后续汇总层完成。

4. **序列化输出**
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。
   先输出结构化 JSON，再附简短自然语言评审。

## 保守评分

- 自研与竞品使用同一维度、同一权重、同一 hard checks；
- 不因为相对胜负而改变绝对评分；
- 不因为链路看起来繁复就自动加分；
- 若链路更好但最终答案没有兑现，优点只能记为链路信号，不能替代答案质量；
- 若答案给错核心数据、时间口径、分析框架、样本范围或结论含义，即便表达更完整也必须扣分并按需触发封顶规则；
- 若双方都没有真正完成用户任务，必须明确输出共同不足，不能把“谁稍微好一点”写成高质量答案。

## 安全护栏

本 skill 的评分安全护栏，尤其包括：
- 诊股查数不是“查到一个字段就结束”。好答案必须完成用户显性任务，并补足金融用户真正关心的口径、对比、解释和可操作观察点；
- 对客观数据题，数据准确、时间口径和样本完整性优先于表达；图表和延伸分析只能加分，不能覆盖核心数据错误；
- 对诊断题，必须使用市场常用分析框架。例如筹码集中度看股东户数变化、大股东持股、机构持仓和筹码分布，而不是孤立搬出一个冷门字段；
- 对“主力”这类多义词，必须覆盖真实语义：大资金数据和龙虎榜/知名席位案例都可能需要检查；
- 对“增长点”要关注增量变化：客户突破、市占率提升、新订单、新业务边际改善、调研纪要或产业数据；只说公司原有业务优秀是存量信息，不等于增长点；
- 对“止盈位”不能只给一个价格，至少要说明技术位、基本面/消息面、风险收益比、仓位或持仓目标；必要时追问用户成本和投资周期；
- 对跨市场品种和商品期货，必须把价格口径、单位、汇率、内外盘价差、基差和合约差异讲清楚；
- 对全市场条件查询，必须严肃检查 SQL/条件解析：上市时间、连续 K 线、节假日前 N 个交易日、“一共涨幅”等容易被模型错解；
- 对数据缺口要诚实。若结构化库没有非公开客户、企业经营数据或分钟成交明细，应主动用搜索、公告、研报、调研纪要等补充；仍无法取得时明确局限，不得编造。
