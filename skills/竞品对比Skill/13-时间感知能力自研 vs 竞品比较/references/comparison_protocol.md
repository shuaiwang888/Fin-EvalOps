# 比较协议层

本文件只定义自研 vs 竞品的 pairwise 比较规则；绝对评分标准由本 skill 的 rubric 体系定义。

## 比较顺序

1. 先确认同题：`case_id` 配对到同一问题，问题文本语义一致。
2. 先抽取共享时间锚点：请求时间、时区、相对时间表达、市场/品种、报告期和数据 as-of 需求。
3. 先对自研与竞品分别做绝对评分。
4. 再比较双方差异。
5. 最后用链路证据解释差异来源。

## 先绝对、后相对

- 不得因为竞品更差，就把自研的绝对短板写成优势。
- 不得因为自研更差，就忽略竞品也没有达到专家标准。
- 若双方都未通过 hard checks，先写 `shared_failures`，再写相对优劣。
- 若双方都合格，再比较谁的日期解析、交易日历核验、as-of 表达、报告期映射和纠错更完整。

## 输出对象的判定规则

### `self_strengths`

仅收录真正成立的我方优势：
- 相对竞品更强；
- 且本身也符合专家标准；
- 且有最终答案或链路证据支撑。

常见来源：
- 更准确地识别用户的相对时间、市场/品种、自然日/交易日或报告期语义；
- 更正确地把“今天/昨天/下周/去年/年中”解析到请求时间对应的绝对日期、年份或期间；
- 更主动核验交易日历、节假日、跨市场时区和行情 as-of；
- 更清楚区分报告期、披露日、公告日、股权登记日、除权除息日和派息实施日；
- 在用户前提错误、目标日休市或数据不可得时，先纠错再给替代口径；
- 更合理的工具组合被成功转化成最终答案中的时间边界说明。

### `self_weaknesses`

收录自研相对竞品或相对专家标准的真实不足：
- 把时间词当作普通修饰语，未改变数据选择或答案口径；
- 日期、星期、年份、报告期或披露期解析错误；
- 休市日仍解释当日涨跌、开盘走势或盘中变化；
- 使用上一交易日、旧公告或旧财报，却没有说明 as-of 或替代口径；
- 链路查对了时间证据，但最终答案没有显式告诉用户；
- 工具链路虽复杂但日期/市场/报告期输入不正确。

### `competitor_strengths`

只写真正值得学习的地方：
- 竞品在最终答案中明显更好地纠正时间前提或标注 as-of；
- 或竞品链路中出现了更优的交易日历、公告/财报、行情日期或跨市场时间核验策略，并最终改善了答案；
- 不能把“篇幅更长”“语气更自信”或“金融分析更多”写成时间感知优势。

### `shared_failures`

双方都没达到专家标准时必须填写。典型情况：
- 都没有使用请求时间/时区解析相对日期；
- 都把休市日当成有交易日回答；
- 都用旧行情或旧财报冒充今天/最新事实；
- 都把自然语言“去年/年中”私自改成数据库最新可得年份；
- 都没有区分自然日、工作日、交易日、报告期和披露期；
- 都没有在用户前提错误时主动纠错。

## 逐维比较

每个活跃维度都要回答三件事：
1. 谁更强 / 是否打平；
2. 差异体现在最终答案的什么地方；
3. 哪段链路证据最能解释这个差异。

推荐优先级：
- `temporal_intent_recognition`：先看谁真正识别了题目中的时间词、市场/品种和时间口径需求；
- `anchor_date_resolution`：看谁把相对时间解析到正确的绝对日期、星期、年份或期间；
- `market_calendar_status`：看谁正确判断目标市场/品种在目标日期是否交易；
- `data_asof_freshness`：看谁核验并表达了数据日期，避免旧数据冒充当前事实；
- `period_disclosure_mapping`：看谁正确处理报告期、披露期、分红流程和替代口径；
- `premise_correction_clarification`：看谁在用户前提错误或模糊时主动纠错；
- `answer_composition_credibility`：看谁在最终答案中清楚呈现时间边界和限制；
- `tool_usage`：看谁的工具选择、查询设计和返回日期读取更适合时间核验。

## 结论语义

- `absolute_summary`：先说双方各自是否通过时间感知专家标准；
- `relative_summary`：再说谁相对更好；
- `verdict=self_better`：我方相对更好，且没有被双方共同失败掩盖；
- `verdict=competitor_better`：竞品相对更好；
- `verdict=tie`：双方接近；
- `verdict=both_poor`：双方都明显不达标，即便一方分数略高，也优先使用该结论。
