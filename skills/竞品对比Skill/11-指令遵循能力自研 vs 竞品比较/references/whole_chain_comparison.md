# 整体链路比较层

本文件说明如何基于真实数据结构比较两边整体链路，并把链路差异解释回最终答案差异。

## 真实输入形状

### 自研模型常见形状

- `text_answer` 通常有值；
- `chain` 通常有多个 step；
- 每个 step 可能包含：
  - `plan`
  - `tools` list
- 工具调用常分散在多个 `chain[N].tools[M]` 中。

### 竞品模型常见形状

- `text_answer` 可能为空；
- 最终答案常在 `answer` 中；
- `chain` 可能只有一个 step；
- `plan` 可能为空字符串；
- 工具调用仍然存在，通常位于 `chain[0].tools`，其值是 list。

## 字段读取原则

- 最终答案主锚点：
  - 自研优先 `text_answer`；
  - 竞品若 `text_answer` 为空，则使用 `answer`。
- `tool_usage` 是评测维度，不是 JSON 字段。
- 工具调用主路径：`chain[N].tools[M]`。
- 顶层 `tools` 即便存在，也可能为 `null`，不能替代 `chain[*].tools[*]`。
- 当 `plan` 为空时，不要臆造不可见推理；直接基于工具行为、工具输出和最终答案做归因。

## 比较什么

整体链路比较不是比较“谁的链路更长”，而是比较谁的链路更能产生高质量指令遵循答案：

1. **指令识别**
   - 是否识别了用户主指令；
   - 是否区分主问和辅助信息；
   - 是否正确识别原因、定义、比较、排序、建议、核实、截止时点等任务类型；
   - 是否把时间、范围、对象、排除项拆成可核验约束。

2. **工具选择**
   - 是否为任务选对了工具；
   - 原因、政策、事件和定义背景是否用 Search 或 AccessingFullText 补足；
   - 行情、板块、个股、指标和时点数据是否用 FinQuery 等结构化工具核验；
   - 多约束整理、计算或比较是否使用 CodeInterpreter 或等价计算校验；
   - 是否避免用 Forecast、BackTest 或纯行情数据替代用户要求的定义、原因或比较结论。

3. **查询设计**
   - 查询词是否贴合用户主指令，而不是只贴合题目中的辅助实体；
   - 是否覆盖用户指定对象、时点、范围和排除条件；
   - 原因题是否查驱动因素，定义题是否查概念边界，比较题是否查差异维度；
   - 是否避免过宽查询导致答案焦点漂移。

4. **证据向答案的转化**
   - 查到的数据是否真正支撑了用户要求的答案类型；
   - 是否存在“链路里查到了信息，答案里却没有回答主问”的断层；
   - 是否存在“工具很多，但最终仍然只输出行情、表格或泛泛背景”的伪复杂；
   - 是否在最终答案中逐项回应关键约束。

## 如何解释答案差异

优先写成“链路动作 -> 答案结果”的形式：
- 因为自研先识别出用户问的是“原因”，并补查政策/事件催化，所以最终没有把涨幅事实误当原因；
- 因为竞品把“流通市值”当成主问，而没有补足微盘股定义，所以最终任务类型错位；
- 因为竞品虽然 `plan` 不可见，但其 `chain[0].tools` 覆盖了指定时点和对象约束，所以最终答案在约束覆盖上更稳；
- 因为自研只把 FinQuery 表格搬进答案，没有转化成定义、原因或比较结论，所以链路没有转化为指令遵循质量。

## 不应做的事

- 不因为自研 chain step 更多，就自动判断其链路更好；
- 不因为竞品 `plan` 为空，就直接把它判成“无推理”；
- 不把 `tool_usage` 误当成 JSON 字段；
- 不只比较工具数量，而忽略这些工具是否真的改善了答案；
- 不把链路中未进入最终答案的信息写成最终答案优势；
- 不把“相关信息更多”误判为“主指令完成更好”。
