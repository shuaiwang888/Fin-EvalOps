# 比较协议层

本文件只定义自研 vs 竞品的 pairwise 比较规则；绝对评分标准由本 skill 的 rubric 体系定义。

## 比较顺序

1. 先确认同题：`case_id` 配对到同一问题，问题文本语义一致。
2. 先从用户问题抽取共享指令框架：主指令、约束、期望答案类型和动态权重。
3. 先对自研与竞品分别做绝对评分。
4. 再比较双方差异。
5. 最后用链路证据解释差异来源。

## 先绝对、后相对

- 不得因为竞品更差，就把自研的绝对短板写成优势。
- 不得因为自研更差，就忽略竞品也没有达到专家标准。
- 若双方都未通过 hard checks，先写 `shared_failures`，再写相对优劣。
- 若双方都合格，再比较谁更完整执行主指令、谁更稳地遵守约束、谁更能把工具结果转化成用户要求的答案类型。

## 输出对象的判定规则

### `self_strengths`

仅收录真正成立的我方优势：
- 相对竞品更强；
- 且本身也符合专家标准；
- 且有最终答案或链路证据支撑。

常见来源：
- 更准确识别用户主指令，而不是被辅助信息带偏；
- 更好地区分原因、定义、比较、排序、建议等任务类型；
- 更完整覆盖时间、对象、范围、排除项等显式约束；
- 答案焦点更贴近主问，没有用数据表、行情事实或背景材料淹没主答案；
- 工具查询围绕主指令设计，并成功转化成原因、定义、比较或决策标准。

### `self_weaknesses`

收录自研相对竞品或相对专家标准的真实不足：
- 漏掉用户主指令或把辅助信息当成主问；
- 把原因题答成行情播报，把定义题答成查询结果，把比较题答成分别介绍；
- 忽略时间、对象、范围、排除项等关键约束；
- 答案焦点漂移，用户仍需追问才能得到主答案；
- 工具链路虽复杂但没有兑现成更好的指令遵循质量。

### `competitor_strengths`

只写真正值得学习的地方：
- 竞品在答案中明显更直接、更贴合主指令或更完整覆盖约束；
- 或竞品链路中出现了更优的主指令核验、证据选择、时点核实、对象约束处理或答案组织策略，并最终改善了答案；
- 不能把“篇幅更长”“措辞更顺”或“模型名气更大”写成优势。

### `shared_failures`

双方都没达到专家标准时必须填写。典型情况：
- 都没有真正回答用户主指令；
- 都把任务类型答错，例如原因题只写上涨事实、定义题只写数据结果；
- 都遗漏关键时间、对象、范围或排除项；
- 都把相关数据堆在答案里，但没有形成用户要求的结论；
- 都用通用模板替代针对本题指令的直接回答。

## 逐维比较

每个活跃维度都要回答三件事：
1. 谁更强 / 是否打平；
2. 差异体现在最终答案的什么地方；
3. 哪段链路证据最能解释这个差异。

推荐优先级：
- `explicit_instruction_completion`：先看谁真正完成了用户主指令；
- `task_type_alignment`：看谁更准确对齐原因、定义、比较、排序、建议等任务类型；
- `constraint_coverage`：看谁更完整遵守时间、范围、对象和排除条件；
- `answer_focus`：看谁更围绕主问组织答案，避免数据堆砌和焦点漂移；
- `necessary_information_completeness`：看谁补足了完成主指令所必需的信息和证据；
- `tool_usage`：看谁的工具选择、查询设计和证据转化更服务于用户主指令。

## 结论语义

- `absolute_summary`：先说双方各自按专家标准好不好；
- `relative_summary`：再说谁相对更好；
- `verdict=self_better`：我方相对更好，且没有被双方共同失败掩盖；
- `verdict=competitor_better`：竞品相对更好；
- `verdict=tie`：双方接近；
- `verdict=both_poor`：双方都明显不达标，即便一方分数略高，也优先使用该结论。
