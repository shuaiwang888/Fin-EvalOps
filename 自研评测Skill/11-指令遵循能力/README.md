# 11-指令遵循能力 Skill

> 自研模型「是否严格完成用户明确指令、任务类型、约束和输出焦点」类问题的评测协议。

---

## 一、Skill 定位与目标

**核心使命**：评测问财模型是否**严格完成用户明确提出的任务、问题类型、约束和输出焦点**。

**关键定位**：

- **主锚点**：`text_answer`
- **辅助证据**：`chain`（只用于工具使用和根因归因）
- **设计哲学**：先抽取**主指令**、**隐含任务类型**、**约束条件**、**输出期望**，再评估答案。**不能因答案有相关数据而忽略指令缺失**。

## 三、适用范围

**适用**：

- 问"**原因/为什么**" → 答案必须**解释驱动因素**，不能只报涨跌数据
- 问"**定义/是什么**" → 答案必须**先解释概念**，不能只给指数/行情/查询结果
- 问"**截止某时点/只看某范围/不要某类**" → 答案必须**遵守时间/范围/排除条件**
- 问"**比较/区别/怎么选/排序**" → 答案必须**按指定任务组织结论**

**不适用**：

- 主要考察金融术语知识但没有明显指令偏离的问题（用 10）

## 四、5 步执行协议

| 步骤 | 动作 | 关键产出 |
|---|---|---|
| **步骤 0** | **抽取指令** + 适用性 + 动态权重 | `weight_assignment`（总和=100） |
| **步骤 1** | **逐项核验**（盲评） | 各维度 `raw_score` + `evidence` |
| **步骤 2** | 链路诊断 + 根因 + `tool_usage` 评分 | `root_causes` |
| **步骤 3** | 应用封顶规则 | `caps` 数组 |
| **步骤 4** | 序列化 JSON 输出 | 按 `output-schema_zh.md` |

**关键步骤强调**：

- **步骤 0**：**先从用户问题中抽取显式指令、隐含任务类型、约束条件和输出期望**，再分配权重
- **步骤 1**：**先看答案是否完成指令，再看数据是否支持**

## 五、6 个评分维度

| 维度 | 建议权重 | 适用性 | 核心关注 |
|---|---:|---|---|
| `explicit_instruction_completion` 显式指令完成 | 30 | **始终 relevant** | 主指令是否被完成（**最高权重**） |
| `task_type_alignment` 任务类型对齐 | 20 | **始终 relevant** | 原因/定义/比较/排序/建议等任务类型是否对齐 |
| `constraint_coverage` 约束覆盖 | 15 | relevant / supplementary | 时间/范围/对象/排除条件 |
| `answer_focus` 答案焦点 | 15 | **始终 relevant** | 是否围绕主问展开，而非数据堆砌或跑题 |
| `necessary_information_completeness` 必要信息完整度 | 10 | relevant / supplementary | 主指令需要证据链时 |
| `tool_usage` 工具使用合理性 | 10 | **始终 relevant** | |

**权重动态调整**：

- 主指令越明确 → `explicit_instruction_completion` 权重越高
- 明确约束越多 → `constraint_coverage` 权重越高
- 若用户只问简单定义 → `task_type_alignment` 和 `answer_focus` 可提高

---

## 六、5 个封顶规则（cap rules）

| 规则 | 上限 | 触发场景 |
|---|---:|---|
| `primary_instruction_missing` 主指令缺失 | **45** | 答案没完成用户主指令（即使内容相关也封顶） |
| `wrong_task_type` 任务类型错误 | **50** | 问原因答涨跌、问定义答指数 |
| `critical_constraint_ignored` 关键约束忽略 | **60** | 忽略时间/范围/对象/排除项 |
| `data_dump_without_instruction_answer` 数据堆砌未回答主问 | **55** | 给了相关数据但不是用户要求的任务 |
| `answer_focus_drift` 答案焦点漂移 | **65** | 把可选补充信息放在核心指令前面，导致用户主问未被回答 |

**重要**：如果答案没有完成用户主指令，**即使内容相关，也必须封顶**。

## 七、5 个 L1 根因归因体系

| L1 | 核心问题 |
|---|---|
| `intent` 意图理解 | 指令识别 |
| `evidence` 证据 | 证据完整 |
| `tool` 工具 | 工具策略 |
| `reasoning` **指令到答案转换** | 指令到答案的转换 |
| `composition` 组织 | 答案组织 |

`reasoning` 在本 skill 中特指**指令到答案的转换根因**，与其他 skill 略有不同。

---

## 八、关键评分原则（安全护栏 5 条）

1. **"原因"题必须解释原因** —— 涨跌幅/资金流/成交额只是证据，不是原因本身
2. **"定义"题必须给概念边界、常用标准和易混点** —— 不能只给查询结果
3. **不要把可选补充信息放在核心指令前面**，导致用户主问未被回答
4. **用户给出时间、对象、范围、排除项时，必须逐项核对**
5. **若答案完成了相关任务但不是用户要求的任务，应按答非所问处理**

---

## 九、常见失败（5 条）

- 问原因，只回答上涨事实
- 问定义，只给指数、行情或查询结果
- 用户要求核实、截止、重新看，却沿用旧数据
- 用户要求比较或区别，却只分别介绍
- 用户指定对象，答案覆盖了泛概念但遗漏对象

## 快速上手 Checklist

1. **步骤 0** **抽取主指令**（**这是本 skill 的关键**）
2. **步骤 1** 重点检查**显式指令完成（30 分，最大权重）**
3. **步骤 2** 检查指令到答案的转换根因
4. **步骤 3** 检查 5 个封顶（**特别注意 `primary_instruction_missing` 上限 45**）
5. **步骤 4** 输出 JSON

**核心方法论**：「**先抽主指令 → 再核验完成度 → 不能因有相关数据就忽略指令缺失**。」
