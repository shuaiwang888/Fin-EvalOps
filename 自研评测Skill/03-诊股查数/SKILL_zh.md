# 诊股查数评测协议

用稳定协议评测我方模型在诊股查数类问题中的表现。以用户问题和最终答案 `text_answer` 为评分主锚点，以完整链路数据用于工具评分、效率判断和根因归因。

## 适用范围

仅在用户问题属于诊股查数、个股/板块数据查询、对比分析或轻量诊断时使用，包括：
- 个股分红、历史行情、涨跌幅、技术指标、资金流、龙虎榜、筹码集中度、客户、订单、增长点、止盈位
- 多标的对比：分红总额、过去 N 年涨跌幅、年度表现差异、行业板块跑赢指数
- 跨市场/跨品种数据：黄金价格、原油内外盘比价、国内期货与海外价格、汇率换算
- 市场统计和宏观金融数据：A 股开户数、新能源车渗透率、行业板块月度表现
- 全市场条件查询：上市时间、涨幅、非 ST、非科创、连续 K 线条件、节前/日前 N 日涨幅
- 用户问法看似简单但隐含诊断框架，例如"主力进场吗""筹码集中度""未来增长点""止盈位"

不适用于事件/概念驱动选股、重度投顾推荐、KYC 适配建议、纯财报业绩归因、复杂策略回测或客服问答；若问题核心是计算回测收益，优先使用回测取数计算 skill。

## 期望输入

每次评测获取：
- 用户问题 `question`
- 我方最终答案，优先使用 `text_answer`
- 完整对话上下文 `context`
- 完整规划链路 `chain`，包括 `plan`、工具调用、工具输入和工具输出
- 可用工具清单 `tools`
- 可选响应耗时、工具调用耗时或时间戳 `timing`
- 可选人工复核反馈、线上维度统计或新增失败样本 `online_dimension_signals`

## 执行协议

0. **分析题目与分配动态权重**  
   阅读 [references/rubric/_index.md](references/rubric/_index.md) 和 [references/golden_cases/_index.md](references/golden_cases/_index.md)。仅根据用户问题判断每个维度适用性：`relevant` / `supplementary` / `not_applicable`。动态权重总和必须为 100，并写入 `weight_assignment`。命中专家案例或同类语义时，必须使用对应 hard checks；未命中具体案例时，也要使用 golden cases 文件末尾的跨案例判分锚点。  
   如果题目涉及图表、截图、可视化对比、多周期展示或工具失败归因，再阅读 [references/golden_cases/image_annotation_anchors.md](references/golden_cases/image_annotation_anchors.md)。

1. **盲评最终答案**  
   以 `text_answer` 为主锚点评分，不因为隐藏链路更好而给最终答案加分。对所有活跃维度输出 `raw_score` 和 `evidence`；不要计算加权分、总分或最终分数。`tool_usage` 例外，在步骤 2 评分；`latency_efficiency` 可依据 `timing` 或链路耗时证据评分，无耗时证据时给中性分并说明。

2. **链路诊断和根因归因**  
   阅读 [references/root-cause/_index.md](references/root-cause/_index.md)，再阅读 [references/tool_list/_index.md](references/tool_list/_index.md)。用 `chain.plan` 判断意图理解、金融分析框架和推理过程；用 `chain.tools[*].input/output` 判断工具选择、结构化数据查询、搜索/公告/研报补充、分时数据、跨市场数据和交叉验证。此时评分 `tool_usage`。根因必须绑定证据。

3. **应用封顶规则**  
   按需读取 [references/rubric/](references/rubric/_index.md) 中的 `cap_*.md` 文件。封顶规则限制最终分，不替代维度评分。多个封顶同时触发时取最低上限。

4. **序列化输出**  
   阅读 [references/output-schema_zh.md](references/output-schema_zh.md)。先输出结构化 JSON，再附简短自然语言评审。

## 保守评分

- 诊股查数不是"查到一个字段就结束"。好答案必须完成用户显性任务，并补足金融用户真正关心的口径、对比、解释和可操作观察点。
- 对客观数据题，数据准确、时间口径和样本完整性优先于表达；图表和延伸分析只能加分，不能覆盖核心数据错误。
- 对诊断题，必须使用市场常用分析框架。例如筹码集中度看股东户数变化、大股东持股、机构持仓和筹码分布，而不是孤立搬出一个冷门字段。
- 对"主力"这类多义词，必须覆盖真实语义：大资金数据和龙虎榜/知名席位案例都可能需要检查。
- 对"增长点"要关注增量变化：客户突破、市占率提升、新订单、新业务边际改善、调研纪要或产业数据。只说公司原有业务优秀是存量信息，不等于增长点。
- 对"止盈位"不能只给一个价格。至少要说明技术位、基本面/消息面、风险收益比、仓位或持仓目标；必要时追问用户成本和投资周期。
- 对跨市场品种和商品期货，必须把价格口径、单位、汇率、内外盘价差、基差和合约差异讲清楚。用经验汇率或模糊规则替代查询应扣分。
- 对全市场条件查询，必须严肃检查 SQL/条件解析：上市时间、连续 K 线、节假日前 N 个交易日、"一共涨幅"等容易被模型错解。
- 对数据缺口要诚实。若结构化库没有非公开客户、企业经营数据或分钟成交明细，应主动用搜索、公告、研报、调研纪要等补充；仍无法取得时明确局限，不得编造。
